## Core Principles

### I. 工程师优先体验（Engineer-First Experience）
所有界面与交互决策 MUST 以 CFD 应用工程师的工作习惯为中心。产品 MUST 呈现高级感：
视觉语言统一、留白与层级克制、动效与反馈即时（交互响应 SHOULD 在 100ms 内给出可视反馈）。
任何新增功能若引入视觉噪音、多余点击层级或与既有交互模式不一致的控件，MUST 提供充分
理由并通过设计评审，否则拒绝合入。可用性缺陷与功能性缺陷同级对待。

### II. 全流程产物管理（Full-Workflow Artifact Management）
软件 MUST 覆盖 CFD 仿真全生命周期的任务与产物：前处理（几何、网格）、求解设置与算例、
求解运行监控、后处理（结果数据、报告）及归档。每个任务 MUST 拥有明确的阶段归属
（例如：待规划 / 进行中 / 待校核 / 已完成 / 已归档），不允许出现无阶段、无负责人的
"悬空"任务或产物。任何阶段的产物 MUST 能关联到其所属任务与上游输入。

### III. 进度透明可规划（Transparent Progress & Planning）
任务进度 MUST 可视、可规划、可重排：用户 MUST 能在统一视图中看到各阶段任务的完成度、
阻塞点与依赖关系。进度状态变更 MUST 及时反映到所有相关视图，禁止出现视图间状态不一致。
规划操作（新建、拆分、依赖调整、优先级变更）MUST 有明确的即时确认反馈。

### IV. 数据可追溯与可靠（Traceability & Data Integrity）
CFD 产物（网格、算例配置、结果、报告）是工程资产。软件 MUST 保证：产物版本可追溯
（谁在何时产生了什么、基于哪个输入）；用户数据在界面刷新、崩溃或升级后 MUST 不丢失、
不损坏。涉及删除、覆盖产物的操作 MUST 经过显式确认。任何静默失败都是缺陷。

### V. 简洁克制（Simplicity & Restraint）
功能设计遵循 YAGNI：先解决工程师当前工作流中最痛的环节，不预建未验证需求的复杂机制。
实现 MUST 从最简方案开始；引入新抽象、新依赖、新配置项时 MUST 说明其直接价值。
"高级感"来自克制的细节打磨，而非功能堆砌。

## 体验与视觉标准

- 设计一致性：所有界面 MUST 遵循统一的设计令牌（色彩、字号、间距、圆角、动效时长），
  禁止在局部私自引入未收编的样式。
- 文案标准：界面文案使用工程师术语（算例、网格、残差、工况等），简洁、无歧义、中英文
  术语全产品统一；错误提示 MUST 说明"发生了什么 + 用户该做什么"。
- 空状态与加载：每个列表/视图 MUST 设计空状态、加载态与错误态，不允许白屏或无解释的
  长时间停滞。
- 大数据量表现：涉及大规模任务列表或产物浏览时，MUST 保持交互流畅，长任务 MUST 提供
  进度指示。
- 评审准入：涉及用户可见的界面改动，MUST 在代码评审中同时接受视觉与交互符合性检查。

## 质量门禁与开发工作流

- 测试先行：核心业务逻辑（任务状态机、产物关联、进度计算）MUST 先写测试再实现
  （红-绿-重构）；纯视觉层不强制，但 MUST 通过手动或快照验证。
- 集成测试范围：任务与产物的数据模型契约、跨视图状态同步、导入/导出链路发生变更时
  MUST 补充或更新集成测试。
- 评审门禁：每次合入 MUST 确认——符合五项核心原则、不违反体验与视觉标准、测试通过、
  无遗留静默失败路径。
- 复杂度 justified：任何超出最简方案的实现 MUST 在评审说明中给出理由与替代方案对比。

## Governance

- 本章程 MUST 覆盖项目中所有其他开发实践与个人偏好；冲突时以章程为准。
- 修订流程：提出修订 → 说明动机与影响面 → 更新章程与版本号 → 同步影响报告 → 全体
  相关者知悉后方可生效。破坏性修订（删除或重定义原则）MUST 附迁移方案。
- 版本策略：MAJOR（原则删除/重定义）、MINOR（新增原则或实质性扩展）、PATCH
  （措辞与澄清）。
- 合规审查：所有 PR/评审 MUST 核对与本章程的一致性；发现的偏离 MUST 当场修复或
  记录为带期限的 TODO。
- 运行时开发细则使用各特性目录下的 plan.md 及实现指南文件，不在本章程中展开。
